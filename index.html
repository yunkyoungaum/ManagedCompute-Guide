Part B · What — Managed Compute란 무엇인가

B1. 3가지 배포 타입, 하나의 엔드포인트

Foundry는 세 가지 배포 타입을 제공하며, 세 가지 모두 동일한 엔드포인트·인증·SDK·프라이빗 네트워크·관측·청구서를 공유합니다. 즉 배포 타입 선택은 아키텍처 결정이 아니라 과금·용량 모델 결정입니다.

배포 타입과금 단위적합한 상황모델 범위
Standard입력/출력 토큰당버스트 트래픽, 가장 낮은 진입 장벽Frontier 중심
Provisioned (PTU)처리량 단위 예약예측 가능한 지속 부하Frontier 중심
Managed Compute 본 가이드가속기 시간당전용 GPU 위 오픈 모델 상시 운영오픈소스 카탈로그 수백 종
핵심 Managed Compute는 "토큰을 사는" 모델이 아니라 "GPU를 시간 단위로 빌리는" 모델입니다. 따라서 자체 VM 운영과 비용 구조가 직접 비교 가능하며, 트래픽이 많을수록 토큰 과금 대비 유리해집니다.

B2. 머신이 아니라 모델을 고른다 — 4-선택 모델

VM 기반 운영에서는 GPU 토폴로지, 텐서 병렬, 런타임 플래그, 컨테이너 이미지, 헬스 프로브, 로드밸런싱을 모두 직접 정해야 합니다. Managed Compute에서는 네 가지만 고르면 Foundry가 나머지 서빙 스택을 구성·운영합니다.

1 · Model

카탈로그 모델과 버전을 선택합니다. 버전이 명시된 레지스트리 자산입니다.

2 · Template

컨텍스트 길이와 서빙 형태를 선택합니다. 런타임·파서·동시성이 이미 튜닝되어 있습니다.

3 · Accelerator

A100 / H100 / MI300X 중 가속기 계열을 선택합니다. VM SKU가 아닙니다.

4 · Instances

처리량·가용성을 위한 모델 인스턴스(레플리카) 수를 정합니다.

Foundry가 대신 결정하는 것

GPU 토폴로지런타임 + 플래그텐서 병렬 컨테이너 이미지헬스 프로브 + 라우트로드 밸런싱

총 GPU 수 = (템플릿당 GPU 수) × (모델 인스턴스 수)

사고방식의 전환 "ND96isr_H100_v5 몇 대가 필요한가?"가 아니라 "H100 몇 개짜리 인스턴스를 몇 개 띄울 것인가?"로 질문이 바뀝니다. 8-GPU 노드에 워크로드를 억지로 패킹하거나 유휴 GPU를 떠안을 필요가 없습니다.

B5. 쿼터 구조와 "플랜 B"

Managed Compute 쿼터는 Azure VM 쿼터와 완전히 분리된 별도 풀이며, 가속기 계열(A100 / H100 / MI300X) 단위로 추적됩니다.

기본 할당

지원 SKU당 8이 기본값입니다. Foundry 포털의 Quota 화면에서 사용량 확인 및 상향 요청이 가능합니다.

분리 원칙

NC/ND 계열 VM 쿼터를 확보하지 못한 상황에서도 Managed Compute 쿼터는 독립적으로 요청·승인됩니다. 기존 Azure VM 쿼터를 Managed Compute에 전용할 수는 없습니다.

C1. 카탈로그에서 엔드포인트까지 5단계

포털, Python SDK, REST 모두 동일한 모델 · 템플릿 · 가속기 · 용량 값을 사용합니다. 일반적인 프로비저닝 시간은 10–15분입니다.

  1. Discover

    모델 카탈로그에서 Deployment option = Managed compute 로 필터하고, Available in my project 로 프로젝트 가용성을 확인합니다. Collection · modality · task · publisher로 추가 필터링이 가능합니다.

  2. Select model

    모델 카드에서 버전이 명시된 레지스트리 자산 ID, 업스트림 라이선스, 지원 태스크, 사용 가능한 배포 옵션을 검토합니다. 라이선스 조건은 그대로 노출되므로 법무 검토에 그대로 사용할 수 있습니다.

  3. Pick template

    런타임, 컨텍스트 길이, GPU 풋프린트 조합을 선택합니다. 예: 16K 컨텍스트 = A100/H100 1개, 256K 컨텍스트 = A100/H100 2개. 템플릿 내부에는 vLLM 버전, tool/reasoning 파서, 동시성 한도, 프로브, 스코어링 경로가 고정되어 있습니다.

  4. Set capacity

    가속기 계열과 모델 인스턴스 수를 지정합니다. 총 GPU 수와 시간당 비용이 여기서 확정됩니다.

  5. Deploy + score

    상태가 Succeeded가 되면 Playground 또는 SDK로 즉시 호출합니다.

화면에서 확인할 것 Step 4 화면의 Model ID와 Deployment template ID는 그대로 복사해 C3의 관리 SDK 코드의 MODEL_ID · TEMPLATE_ID에 넣으면 됩니다. 포털과 SDK가 동일한 값을 사용합니다.

D3. 킬러 지표 — $ / 1M 토큰 산출법

$ / 1M output tokens = (시간당 단가 × 인스턴스당 GPU 수) ÷ (실측 output TPS × 3600) × 1,000,000

계산 예시

H100 1개 인스턴스($7.91/h)에서 목표 동시성 기준 실측 output 처리량이 2,000 tok/s라면:

시간당 생산 토큰 = 2,000 × 3,600 = 7,200,000 tokens
$ / 1M tokens     = 7.91 ÷ 7.2 ≈ $1.10

동일 워크로드에서 MI300X가 메모리 여유로 2,800 tok/s를 낸다면 $7.91 ÷ 10.08 ≈ $0.78 로 약 29% 개선됩니다. 단가가 같으므로 처리량 우위가 그대로 비용 우위가 됩니다.

  • SLO를 고정한 상태의 처리량을 쓰세요. TTFT p95 < 목표치를 만족하는 최대 동시성에서의 TPS가 유효한 값입니다. SLO 없이 뽑은 최대 처리량은 실서비스에서 재현되지 않습니다.

Part B · What — What is Managed Compute

B1. Three deployment types, one endpoint

Foundry offers three deployment types, and all three share the same endpoint, authentication, SDK, private networking, observability, and invoice. In other words, choosing a deployment type is not an architecture decision but a billing and capacity model decision.

Deployment typeBilling unitBest forModel scope
StandardPer input/output tokenBursty traffic, lowest barrier to entryFrontier-focused
Provisioned (PTU)Reserved throughput unitsPredictable, sustained loadFrontier-focused
Managed Compute this guidePer accelerator-hourContinuous operation of open models on dedicated GPUsHundreds of open-source catalog models
Key point Managed Compute is not a "buy tokens" model but a "rent GPUs by the hour" model. As a result, its cost structure is directly comparable to self-operated VMs, and the more traffic you have, the more favorable it becomes versus token-based billing.

B2. You pick a model, not a machine — the 4-choice model

In VM-based operations you must decide the GPU topology, tensor parallelism, runtime flags, container image, health probes, and load balancing yourself. In Managed Compute you choose just four things and Foundry configures and operates the rest of the serving stack.

1 · Model

Select a catalog model and its version. It is a registry asset with an explicit version.

2 · Template

Select the context length and serving shape. Runtime, parser, and concurrency are already tuned.

3 · Accelerator

Select the accelerator family among A100 / H100 / MI300X. It is not a VM SKU.

4 · Instances

Set the number of model instances (replicas) for throughput and availability.

What Foundry decides on your behalf

GPU topologyRuntime + flagsTensor parallelism Container imageHealth probes + routesLoad balancing

Total GPUs = (GPUs per template) × (number of model instances)

A shift in mindset The question is no longer "how many ND96isr_H100_v5 do I need?" but "how many instances of how many H100s should I run?" There is no need to force-pack a workload onto an 8-GPU node or carry idle GPUs.

B5. Quota structure and "Plan B"

Managed Compute quota is a separate pool completely isolated from Azure VM quota, and it is tracked per accelerator family (A100 / H100 / MI300X).

Default allocation

8 per supported SKU is the default. You can check usage and request increases on the Quota screen in the Foundry portal.

Isolation principle

Even when you have not secured NC/ND-series VM quota, Managed Compute quota is requested and approved independently. You cannot dedicate existing Azure VM quota to Managed Compute.

Unit

Granted per accelerator family × region. There is no need to reason about vCPU · VM-series combinations.

Part C · How — Migration hands-on

C1. From catalog to endpoint in 5 steps

The portal, Python SDK, and REST all use the same model · template · accelerator · capacity values. Typical provisioning time is 10–15 minutes.

  1. Discover

    Filter the model catalog by Deployment option = Managed compute, and confirm project availability with Available in my project. You can further filter by collection · modality · task · publisher.

  2. Select model

    On the model card, review the version-pinned registry asset ID, the upstream license, supported tasks, and available deployment options. License terms are surfaced as-is, so you can use them directly for legal review.

  3. Pick template

    Select the combination of runtime, context length, and GPU footprint. Example: 16K context = 1 A100/H100, 256K context = 2 A100/H100. Inside a template, the vLLM version, tool/reasoning parser, concurrency limit, probes, and scoring path are pinned.

  4. Set capacity

    Specify the accelerator family and the number of model instances. The total GPU count and hourly cost are finalized here.

  5. Deploy + score

    Once the status becomes Succeeded, call it immediately from the Playground or SDK.

What to check on screen Copy the Model ID and Deployment template ID from the Step 4 screen directly into the MODEL_ID · TEMPLATE_ID of the management SDK code in C3. The portal and SDK use the same values.

C3. Code migration — you change two lines

If you were using your own vLLM OpenAI server, the only application changes are the base URL and authentication.

Before — self-hosted vLLM endpoint

from openai import OpenAI

client = OpenAI(
    base_url="http://vllm-svc.internal:8000/v1",
    api_key="EMPTY",
)

resp = client.chat.completions.create(
    model="/models/my-model",   # local mount path
    messages=[{"role": "user", "content": "..."}],
)

After — Foundry unified endpoint

from azure.identity import DefaultAzureCredential, get_bearer_token_provider
from openai import OpenAI

token_provider = get_bearer_token_provider(
    DefaultAzureCredential(), "https://ai.azure.com/.default"
)

client = OpenAI(
    base_url=f"https://{ACCOUNT}.services.ai.azure.com/openai/v1",
    api_key=token_provider,
)

resp = client.chat.completions.create(
    model="gemma-4-31b",        # ← deployment name (not the catalog model ID)
    messages=[{"role": "user", "content": "..."}],
)
print(resp.choices[0].message.content)
The most common mistake The model= field must contain the deployment name, not the catalog model ID. Also, models with a custom route rather than an OpenAI-compatible path use the /managed-deployments/<deployment-name>/ path.

Deployment automation — management SDK (IaC replacement)

from azure.identity import DefaultAzureCredential
from azure.mgmt.cognitiveservices import CognitiveServicesManagementClient

client = CognitiveServicesManagementClient(
    DefaultAzureCredential(), SUBSCRIPTION_ID)

poller = client.managed_compute_deployments.begin_create_or_update(
    resource_group_name=RESOURCE_GROUP,
    account_name=ACCOUNT_NAME,
    deployment_name="gemma-4-31b",
    resource={
        "sku": {"name": "GlobalManagedCompute", "capacity": 1},   # number of model instances
        "properties": {
            "model": MODEL_ID,                    # versioned catalog asset
            "deploymentTemplate": TEMPLATE_ID,    # runtime · context · GPU footprint
            "acceleratorType": "H100_80GB",     # not a VM SKU
        },
    },
)
deployment = poller.result()

Your existing Terraform/Bicep AKS node pool + Helm chart definitions are replaced by this single block. Scaling out is just changing capacity.

C6. Scale-out and cache-aware routing

In a self-hosted stack you had to implement the gateway, router, and session affinity yourself, but the Foundry router balances the outstanding prompt token load while simultaneously preserving cache validity and session locality.

Prompt cache

Reuses KV state for repeated prefixes.

Prefix affinity

Routes shared prompts to a warmed replica.

Session affinity

Keeps related turns on the same instance as far as load allows.

Load-aware spillover

When the preferred replica is busy, exceeds the soft load limit to protect balance.

The only scaling lever is changing the number of model instances. No adding nodes, tuning the scheduler, or reconfiguring the router is required.

D3. The killer metric — how to calculate $ / 1M tokens

$ / 1M output tokens = (hourly rate × GPUs per instance) ÷ (measured output TPS × 3600) × 1,000,000

Worked example

If a single-H100 instance ($7.91/h) delivers a measured output throughput of 2,000 tok/s at the target concurrency:

Tokens produced per hour = 2,000 × 3,600 = 7,200,000 tokens
$ / 1M tokens            = 7.91 ÷ 7.2 ≈ $1.10

If, for the same workload, MI300X delivers 2,800 tok/s thanks to memory headroom, then $7.91 ÷ 10.08 ≈ $0.78, an improvement of about 29%. Since the rate is the same, the throughput lead becomes the cost lead directly.

Cautions when measuring
  • Use throughput at a fixed SLO. The valid figure is the TPS at the maximum concurrency that still satisfies TTFT p95 < target. Maximum throughput measured without an SLO does not reproduce in production.
  • Match the input/output token ratio to real traffic. Prefill-heavy RAG and decode-heavy chat produce very different results.
  • In multi-turn scenarios, ContextTokensCacheMatchRate rises, so recompute using effective throughput that includes the cache effect.
